# 经验集

> 从「让 AI 做一个 Minecraft mod」这件事里，能带走去别处用的做法。
> 不记失误（那些在 `AI-LOG.md`），只记**下次该怎么开局、怎么推进、怎么验收**。

---

## 1. 开局：先验环境，再谈方案

**一句话**：卡死设计的从来不是想法，是环境。

本项目在写第一行代码之前，跑了一次探测矩阵，三个结果直接重排了方案：

- `maven.neoforged.net` 20 秒超时 0 字节 → **本地构建这条路不存在**，一切围绕 CI 设计
- `%APPDATA%\.minecraft` 没有 `versions/` → 默认实例不是真实例，得去找 PCL 的隔离目录
- 机器上没有 ollama、没有 API key → 「本地跑模型」的选项当场出局

**做法**：动手前花 5 分钟，把所有外部依赖逐个探一遍（网络、JDK、缓存、仓库、游戏实例），
把结论写成一张表。**表里每一个 ❌ 都是一个不用走的岔路。**

## 2. 抄一个「已经绿过」的骨架，别抄裸模板

`irons-addon` 有 4 次成功构建产物，`neoforge-1.21.1` 裸模板一次都没构建过。
抄前者，把「能不能出 jar」这件事从赌局变成已知；代码从零写，把别人的业务逻辑挡在门外。

**判据**：骨架的价值不是「好看」，是「它在这台机器上绿过」。

## 3. 第一个提交只放最小可编译集

v0.1 的第一个 push 只包含：构建文件 + 一个 `@Mod` 入口 + 两个事件类。
目的不是功能，是**让 CI 先绿一次**，把「构建链路」和「功能代码」这两类问题分开。

如果第一个 push 就塞十个功能，红了之后你分不清是 gradle 配置错还是代码错。

## 4. CI 绿 ≠ 能用

`build/libs/*.jar` 非空只证明「编译通过、资源打进去了」。
它证明不了：配方在游戏里是否被识别、事件是否真的触发、贴图路径大小写对不对。

**所以验收必须分层**：

| 层 | 谁验 | 能发现什么 |
|---|---|---|
| 编译 + 打包 | CI | API 拼写、语法、资源没进 jar |
| 资源完整性 | 解 jar 看 entries | 缺 lang、贴图路径错、`data/` 没打进去 |
| 注册表加载 | 游戏启动日志 | 注册冲突、mods.toml 写错、依赖版本不满足 |
| 行为正确 | 进世界实操 | 配方认不认、事件触不触发、数值对不对 |

**AI 只能可靠地覆盖前两层。** 后两层必须有人进游戏 —— 这就是为什么要先找到实例路径。

## 5. 需求复述：听到「学习 X」先问是哪一种

「学习 X」至少三种读法：把 X 做成内容 / 用 X 干活 / 研究 X 本身。
本项目在这上面浪费了整整两轮方案设计。

**规矩**：遇到元目标（学习、练习、熟悉、顺便、试试）先复述一遍再动手，
一句话的成本，换掉两轮返工。

## 6. 决策权分层：产品方向归人，技术细节归 AI

用户明确说过「这种问题之后太多了我不希望你反复问我」。
于是把决策切成两类：

- **产品方向**（做什么、给谁、多难、要不要平衡）→ 每轮 2–3 个，人拍板
- **技术细节**（用哪个 API、类怎么拆、变量怎么命名）→ AI 自己定，错了记进错题本

好处：不浪费人的注意力，也不让 AI 在无意义的确认上打转。

## 7. 不确定就当场说「我猜的」，让 CI 当裁判

`Level#getMoonPhase()` 的签名是凭记忆写的。写成注释里的自述，比写完假装确定更有价值 ——
因为后面日志里真出问题时，你立刻知道从哪儿开始查。

**模板**：「这个 API 我不确定，等 CI 判。如果红在 X 行，说明是 A 而不是 B。」

## 8. 每个功能独立可关

不是洁癖，是**回滚成本**。一个功能炸了，玩家关掉它就能继续玩，而不是卸整个 mod。
从第一版就留开关，比事后加便宜得多。

## 9. 先把「不做什么」写下来

本项目的「不做清单」比「做清单」长：新矿石、新维度、新怪、worldgen、GUI、任务书。
写下来不是为了限制，是为了**下次有人（包括 AI）提议时，有一条现成的判据可以引用**。
